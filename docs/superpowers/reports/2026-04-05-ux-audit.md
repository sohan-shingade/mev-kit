# mev-kit Web UI -- Comprehensive UX Audit

**Date:** 2026-04-05
**Auditor:** Claude Code (Opus 4.6)
**Server tested:** http://localhost:8080
**Codebase version:** Current HEAD, all pages and API endpoints tested

---

## 1. Executive Summary

The mev-kit web UI is a strong technical foundation with a clean dark aesthetic appropriate for its trading-tool audience. The 7-page structure covers the key workflows. However, testing every page and API endpoint reveals significant friction points that will slow adoption across all three personas. The most critical findings:

- **Backtests always return zero trades with Binance data.** The CEX-DEX arb detector expects two concurrent data sources (DEX pool state + CEX price), but the backtest pipeline feeds only one Parquet file. Users will run their first backtest, see zero results, and assume the product is broken. This is the single biggest adoption blocker.
- **No onboarding flow or landing state.** First launch drops users on an empty Dashboard with all panels showing "No opportunities yet" and dashes. There is no guided setup wizard, no "start here" prompt, no auto-detection of whether data files exist.
- **The Dashboard landing page is confusing when idle.** Seven panels of empty placeholders create the impression the tool is non-functional rather than "not yet started."
- **Paper trading fails silently.** Starting paper mode returns "started" but the pipeline immediately goes idle -- likely due to adapter connection failures. The UI shows no error, just returns to showing dashes.
- **Config page and Backtest page duplicate strategy params** (min_spread_bps, fee_bps, position_size_sol) with no indication of which takes precedence.
- **The Analysis page has a hard dependency on SQLite databases** that don't exist until paper trading or backtest results are persisted -- and backtests currently write to an in-memory sink that never creates the DB files the Analysis page expects.
- **LogStream panel is a stub.** It displays static placeholder text ("Log streaming via WebSocket -- connect to /ws/logs") and never renders actual log data.
- **HotParams panel uses hardcoded initial values** rather than reading from the active config or running pipeline.
- **Strategy Editor "New Strategy" uses browser `prompt()`** -- a jarring UX break in an otherwise polished UI.
- **CSV export in Analysis only exports the current page** (50 trades), not the full dataset. The filename says `trades_results.db_page1.csv` which is confusing.

## 2. Customer Journey Maps

### Persona 1: Solo MEV Searcher

**Goal:** Write a custom arb detector, backtest it against historical data, then run it live.

**Ideal journey:**
1. Install mev-kit, run `mev-kit ui` --> Land on Dashboard
2. See an immediate "Getting Started" prompt directing to Data page
3. Fetch 7 days of SOL/USDT data from Binance (takes ~10 seconds)
4. Navigate to Backtest, select data file, select CEX-DEX Arb, run
5. See results with trades, P&L chart, trade table
6. Navigate to Strategies, click "New Strategy", get template with working example
7. Edit strategy, validate, save
8. Re-run backtest with custom strategy, compare results
9. Set HELIUS_API_KEY, switch to paper trading on Dashboard
10. Monitor live opportunity feed, adjust hot params
11. After paper validation, switch to live mode with small position

**Current friction points:**
- Step 2 does not exist -- user sees empty dashboard
- Step 4 returns zero trades (detector/data mismatch)
- Step 9 requires leaving the UI to set env vars, then restarting the server
- Step 10 pipeline fails silently

### Persona 2: Quant Trading Desk

**Goal:** Run multiple strategies, compare backtest results across param sets, share configs.

**Ideal journey:**
1. Clone repo, install, each team member runs their own UI
2. Create config profiles (conservative, aggressive, experimental)
3. Fetch diverse data sets (SOL/USDC, mSOL/SOL, different time windows)
4. Batch backtest across strategies and param grids
5. Compare results side-by-side
6. Share best configs via TOML files in version control
7. Deploy paper trading with selected strategy, monitor dashboard
8. Promote to live with risk controls

**Current friction points:**
- Step 4: No batch/parallel backtest capability -- one at a time only
- Step 5: No comparison view -- must manually record results from each run
- Step 6: Config save works but profiles aren't clearly exportable
- Step 7: Cannot select which strategy to use for paper/live from Dashboard -- it's hardcoded to CEXDEXArbDetector in PipelineManager

### Persona 3: MEV Beginner

**Goal:** Learn MEV concepts, understand what mev-kit does, run a safe experiment.

**Ideal journey:**
1. Install, launch UI
2. See helpful landing page explaining what to do first
3. Navigate to Learn, read Getting Started guide
4. Follow guide step-by-step: fetch data, run backtest, view results
5. Read CEX-DEX Arb guide to understand the strategy
6. Try adjusting parameters and re-running
7. Graduate to paper trading with hand-holding

**Current friction points:**
- Step 2: No landing guidance
- Step 3: Learn page works well -- this is a strong part of the UX
- Step 4: Guide references `scripts/fetch_binance_history.py` which is not the same as the Data page fetch flow -- creates confusion about which path to use
- Step 4: Backtest returns zero trades, breaking the tutorial flow
- Step 6: No "try these settings" suggestions or preset parameter bundles

## 3. Workflow Analysis

### Workflow 1: First-Time Setup

**Current state (step-by-step):**
1. User runs `mev-kit ui`, opens http://localhost:8080
2. Dashboard loads with: PipelineControls (Paper/Live dropdown + Start button), MetricsStrip (all dashes), PnlChart (empty), SpreadHistogram (empty), OpportunityFeed ("No opportunities yet"), LivePrices (all dashes), HotParams (hardcoded values), LogStream (stub text)
3. No indication of what to do first
4. No detection of missing data files or missing API keys

**Pain points:**
- The Dashboard is the wrong landing page for a first-time user. It's a monitoring page for an active pipeline, not an onboarding page.
- Seven empty/placeholder panels communicate "this tool doesn't work" rather than "this tool is waiting for you to set it up."
- The nav sidebar has icon-only labels (tooltip on hover) -- new users must hover each icon to discover what pages exist.
- No visual hierarchy guiding the user to the Learn or Data page first.

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 1.1 | Add a first-time-setup overlay or onboarding banner on Dashboard that detects: (a) zero data files, (b) zero results DBs, (c) no API keys set. Show a 3-step checklist: "1. Fetch data (Data page) 2. Run a backtest (Backtest page) 3. Analyze results (Analysis page)" with direct links. Dismiss when all steps are complete. | P0 |
| 1.2 | Add text labels next to nav icons, or at minimum show labels on first visit (collapsible sidebar). The 52px icon-only sidebar is compact but hostile to new users. | P1 |
| 1.3 | Change the default landing route for first-time users (no localStorage data) to the Learn page or a dedicated Welcome page instead of Dashboard. | P2 |

### Workflow 2: Download Historical Data

**Current state (Binance flow):**
1. User navigates to Data page (Database icon in nav)
2. Sees file table (empty or populated), then two fetch forms side by side
3. "Fetch Binance OHLCV" form: Symbol Preset dropdown (7 options), Symbol text input (synced), Interval dropdown (1m/5m/15m/1h/4h/1d), Days input, Use Binance US checkbox
4. Click "Fetch Binance Data" -- toast says "Binance fetch started"
5. Fetch Jobs section appears below with progress bar
6. On completion, file appears in the table above

**What works well:**
- Preset dropdowns for common symbols and pool addresses reduce errors
- Progress tracking with live updates via polling
- Clean completion state showing row count and filename
- Auto-refresh of file list on job completion

**Current state (Helius historical flow):**
1. "Fetch Historical (Raydium)" form: Pool Preset dropdown (7 pools), Pool Address input, Poll Interval (5s to 5m), Duration (1m to 1h)
2. Yellow info box explains "Live polling -- fetches current on-chain state at each interval"
3. Click "Fetch Historical Data"
4. Requires HELIUS_API_KEY -- returns error toast if not set

**Pain points:**
- **Binance fetch has no "1s" interval option** in the dropdown even though the Getting Started guide recommends 1s data. The dropdown options are: 1m, 5m, 15m, 1h, 4h, 1d.
- **Helius fetch is real-time polling, not historical retrieval.** "5 min duration = 5 min to complete" is stated in the info box but easily missed. A user expecting to quickly grab historical data will be confused when a "5 minute" fetch takes 5 actual minutes.
- **No upload capability.** If a user has a Parquet file from elsewhere, there's no way to upload it through the UI. They must manually copy it to the `./data/` directory.
- **File table "Modified" column shows raw epoch timestamps** formatted via `toLocaleString()`, which works but the column label "Modified" is ambiguous (modified when? fetched when?).
- **No indication of which files are compatible with which strategies.** Binance data (OHLCV format) and Raydium data (pool state format) have different schemas, but the Backtest page lists all files in one dropdown without differentiating.

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 2.1 | Add "1s" interval option to Binance fetch dropdown. The CEX-DEX arb strategy benefits from high-frequency data and the guide recommends it. | P0 |
| 2.2 | Add a drag-and-drop file upload zone on the Data page for importing external Parquet files. | P1 |
| 2.3 | Tag files with their schema type (binance_ohlcv, raydium_pool, etc.) based on column inspection. Display as a badge in the file table. | P1 |
| 2.4 | Rename the Helius section from "Fetch Historical" to "Live Pool Polling" to set correct expectations. Add estimated completion time. | P1 |
| 2.5 | Add a "time remaining" estimate to running fetch jobs based on progress/total. | P2 |

### Workflow 3: Run a Backtest

**Current state:**
1. Navigate to Backtest page
2. If no data files: italic message "No Parquet files found -- upload via the Data page first" (good empty state)
3. If files exist: dropdown populated, first file auto-selected
4. Strategy dropdown: "CEX-DEX Arb" (builtin) plus any user/example strategies from `/api/strategies/files`
5. Parameter grid: Min Spread (bps), Fee (bps), Position Size (SOL), Simulate before execute checkbox
6. Click "Run Backtest" -- view transitions to "Backtest Running" with progress (updates processed, opportunities detected) and an animated progress bar
7. On completion: summary cards + paginated trade table

**Critical bug: Zero trades on all tested runs.**
I ran backtests via both the UI endpoint and direct curl against `test_backtest.parquet` (20 rows, Raydium pool format) and `binance_solusdt_1m_20260405_073121.parquet` (10,080 rows, Binance OHLCV format). Both returned 0 trades. Root cause: The CEX-DEX arb detector needs simultaneous DEX and CEX price feeds to compute a spread. A single Parquet replay provides only one feed. With only one price source, the spread is always 0, so no opportunities are ever detected.

**Pain points:**
- **Zero trades is the default outcome** for any first-time user following the docs. This is the single biggest adoption blocker.
- **Progress bar is fake.** The bar width is calculated as `(updates_processed / 10000) * 100%` -- a hardcoded denominator of 10,000. For a 20-row file it shows ~0.2%; for a 10,080-row file it shows 100.8% (clamped). The actual total row count is available from the data file metadata but not used.
- **No error display for zero-trade backtests.** The completed state shows "Total Trades: 0" and all other metrics as 0. There's no message explaining why zero trades occurred or suggesting parameter adjustments.
- **The "Tweak & Re-run" button works** but resets to the config form without preserving which data file and strategy were selected (it re-reads from the API, so the selection is preserved in practice, but the params revert to defaults rather than the last-used values).
- **Backtest page duplicates strategy params** that also exist on the Config page (min_spread_bps, fee_bps, position_size_sol). It's unclear whether the Backtest page params override the Config page values or vice versa. (Answer from code: the Backtest page sends its own params directly, ignoring the Config page.)
- **No param validation.** Negative spread, zero position size, spread lower than fee -- none of these are caught or warned about.
- **Cannot select a strategy that's not yet saved.** If a user writes a custom strategy in the editor but hasn't saved it, it won't appear in the Backtest strategy dropdown.
- **The backtest endpoint accepts a start with a nonexistent file** and only errors asynchronously -- the UI shows "Running" briefly then transitions to an error state. The error message includes a double-slash in the path: `./data//nonexistent.parquet`.

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 3.1 | **Fix the zero-trade problem.** The backtest needs to work with the data users can actually fetch. Two approaches: (a) Ship a synthetic combined Parquet with both DEX and CEX columns so the CEX-DEX arb works out of the box, or (b) Create a simpler "single-source" example detector (e.g., spread_tracker or momentum_detector) that works with Binance-only data, and make it the default strategy for backtests. | P0 |
| 3.2 | Add an explanatory message when backtest completes with 0 trades: "No opportunities detected. This usually means: (1) min_spread_bps is higher than any spread in the data, (2) the data file lacks the columns this strategy needs, or (3) the data window is too short. Try lowering min_spread_bps or using a different data file." | P0 |
| 3.3 | Compute actual total rows from the selected data file and use it for the progress bar denominator instead of hardcoded 10,000. | P1 |
| 3.4 | Persist the last-used backtest params in localStorage and restore them when the user clicks "Tweak & Re-run" or revisits the page. | P1 |
| 3.5 | Add client-side validation: warn if min_spread_bps < fee_bps (guaranteed unprofitable), warn if position_size_sol is 0 or negative. | P1 |
| 3.6 | Validate the data file exists before returning "started" from POST /api/backtest/start. Return an immediate error response instead of async error. Fix the double-slash in path construction. | P1 |
| 3.7 | Add a "View in Analysis" button on the backtest results page that navigates to /analysis with the results pre-loaded, or saves results to a DB that the Analysis page can read. | P2 |
| 3.8 | Clarify the relationship between Backtest page params and Config page params -- either remove the duplication (Backtest reads from Config) or add a "Use config profile" toggle. | P2 |

### Workflow 4: Write a Custom Detector

**Current state:**
1. Navigate to Strategies page (Code2 icon in nav)
2. Left sidebar: "Your Strategies" section (user .py files) and "Examples" section (5 example detectors)
3. Click an example to view in Monaco editor (read-only, shown with amber "READ ONLY" badge)
4. Click "+" (New Strategy) -- browser `prompt()` asks for filename
5. Template code loads in editor with a CustomDetector skeleton
6. Right panel shows: Validation status, Required Data Sources (parsed from code), Quick Reference (API methods)
7. Toolbar: Validate button (checks Python syntax), Save button (saves to strategies dir)

**What works well:**
- Monaco editor with Python syntax highlighting is excellent for the target audience
- Read-only examples prevent accidental modification
- Validation with line-number error reporting is useful
- Quick Reference panel reduces context-switching to docs
- Data source detection (parsing `required_sources`) from code is clever and helpful

**Pain points:**
- **`prompt()` for new file creation** is a jarring UX regression. Should be an inline modal or form matching the rest of the UI.
- **No "Copy example to my strategies" flow.** Users want to fork an example, not write from scratch. Currently they must manually copy-paste code from an example file into a new file.
- **Validation only checks syntax** (Python `compile()`), not whether the strategy is importable or whether it actually subclasses Detector correctly. A file that `import`s a missing module will validate as "valid" but fail at backtest time.
- **No keyboard shortcut for save.** Developers expect Cmd/Ctrl+S. The Monaco editor supports custom key bindings but they aren't wired up.
- **Cannot delete a user strategy from the UI.** No delete button, no context menu.
- **The right panel "Required Data Sources" section only works if the code uses the exact pattern `required_sources = {Source.X, Source.Y}`.** Any variation (multi-line, variable assignment, different formatting) won't be detected by the regex.
- **No indication of which strategies are compatible with which data files.** The Backtest page strategy dropdown doesn't warn if the selected strategy requires data sources that aren't in the selected data file.
- **Editor height is 100% of viewport** minus the toolbar, which is correct, but there's no split-view or tab capability for comparing two strategies side-by-side.

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 4.1 | Replace `prompt()` with an inline modal matching the UI design system. Include filename input, strategy type suggestion, and a "Start from template" vs "Copy from example" choice. | P0 |
| 4.2 | Add a "Fork this example" button when viewing an example strategy. Creates a user copy with a suggested filename. | P1 |
| 4.3 | Add Cmd/Ctrl+S keyboard shortcut for save via Monaco's `addAction` API. | P1 |
| 4.4 | Add a delete button with confirmation modal for user strategies in the sidebar. | P1 |
| 4.5 | Enhance validation to attempt an actual import (in a subprocess or safe eval) and report import errors, not just syntax. | P2 |
| 4.6 | Show a "Run backtest with this strategy" shortcut button in the editor toolbar that navigates to Backtest with the strategy pre-selected. | P2 |

### Workflow 5: Analyze Results

**Current state:**
1. Navigate to Analysis page
2. DB selector dropdown: results.db, backtest.db, paper_trade.db (hardcoded in frontend)
3. All three DBs return "Database not found" -- no DB files exist in ./data/
4. Empty state message: "No results database found for [db name]. Run a backtest or paper trade first to generate results, then come back here to analyze them."
5. When a DB exists (tested manually): summary cards, three charts (P&L Over Time, Spread Distribution, Direction Breakdown), paginated trade table with sort/filter controls, CSV export

**Pain points:**
- **Analysis page is always empty for new users** because: (a) Backtests write results to an in-memory BacktestSink and return them inline -- they never create a SQLite DB. (b) Paper trading would create results.db but paper mode fails silently. So the Analysis page is unreachable in the current flow.
- **DB selector is hardcoded to three filenames.** If results are written to `./data/results.db`, it appears, but if the path is configured differently in Config (e.g., `./data/paper_results.db`), the Analysis page can't find it.
- **Charts use only the current page of trades** (50 per page), not the full dataset. This is noted in a small italic message below the charts, but users will likely miss it and draw wrong conclusions from partial data.
- **CSV export exports only the current page.** The filename includes `page1` but there's no "Export All" option. A quant desk analyzing 10,000 trades must paginate and export 200 times.
- **No Sharpe ratio, max drawdown, or profit factor** -- metrics that quant desks consider essential for strategy evaluation.
- **No comparison capability.** Cannot view two backtest runs side-by-side.
- **Sort options are limited to three columns** (Time, Spread, Profit). Cannot sort by Direction or DEX.

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 5.1 | **Connect backtest results to Analysis.** Either: (a) have BacktestSink write to a SQLite DB that Analysis can read, or (b) add an in-memory results store that the Analysis page queries via a separate API endpoint (not the SQLite path). The backtest results already exist in `_runner._results` -- expose them through `/api/analysis/backtest` without requiring a file on disk. | P0 |
| 5.2 | Dynamically discover available DB files from the data directory instead of hardcoding three filenames. Scan for `*.db` files. | P1 |
| 5.3 | Add a "Export All (CSV)" button that fetches all trades server-side and returns a downloadable CSV. The current page-based export is insufficient for any serious analysis. | P1 |
| 5.4 | Compute charts from the full dataset server-side and return pre-aggregated data, rather than computing from 50 client-side trades. | P1 |
| 5.5 | Add key quant metrics: Sharpe ratio, max drawdown, profit factor, average win/loss ratio, max consecutive wins/losses. | P1 |
| 5.6 | Add a "Compare Runs" view where users can select two result sets and see metrics side-by-side with delta highlighting. | P2 |
| 5.7 | Add sortable column headers in the trade table (currently disabled with `sortable={false}`). | P2 |

### Workflow 6: Configure and Start Paper Trading

**Current state:**
1. Navigate to Config page
2. Profile selector: free, pro, test, testbug, testfix (all profiles found in config/)
3. Accordion sections: Strategy (4 fields), Adapters (6 checkboxes), Simulator (2 fields), Sink (2 fields), Risk (3 fields), API Keys (6 env var status indicators)
4. Save and Save As buttons at top
5. API Keys section shows SET/MISSING badges for each env var -- good UX

**Starting paper trading:**
1. Go to Dashboard
2. Select "Paper" from mode dropdown
3. Click "Start"
4. Pipeline starts, then immediately drops back to idle (tested via API)

**Pain points:**
- **Paper trading start fails silently.** POST /api/pipeline/start returns `{"status":"started","mode":"paper"}` but the pipeline dies immediately. The Dashboard shows no error -- just reverts to idle state. Root cause likely: HeliusWSAdapter or BinanceWSAdapter connection failure.
- **No way to select which strategy to use for paper/live trading.** The PipelineManager hardcodes CEXDEXArbDetector. The Config page has a strategy section but PipelineControls doesn't read from it.
- **No way to select which config profile to use when starting the pipeline.** PipelineControls sends `{ mode: selectedMode, config: {} }` -- an empty config object. The pipeline ignores the Config page settings.
- **Config page has no "Apply and Start" button** that would save config, then start the pipeline with those settings.
- **Cannot set API keys from the UI.** API Keys section is read-only (intentional for security, but inconvenient). Users must exit the UI, set env vars in their shell, and restart the server. No guidance on how to do this is shown in the UI.
- **Adapter checkboxes in Config are disconnected from the pipeline.** Checking/unchecking adapters in Config doesn't affect which adapters PipelineManager instantiates.
- **Sink type selection in Config is disconnected.** Changing the sink type in Config doesn't affect the pipeline, which always uses PaperTradeSink in paper mode and JitoBundleSink in live mode.
- **Save As creates a new profile** but there's no way to delete a profile from the UI.

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 6.1 | Surface pipeline start/stop errors in the UI. When the pipeline task dies, detect it (task.done() with exception) and push an error event via the WebSocket. Display a red error banner on the Dashboard with the exception message. | P0 |
| 6.2 | Add a config profile selector to PipelineControls so users can pick which config profile to start with. Pass the profile name or merged config to the start endpoint. | P0 |
| 6.3 | Add a strategy selector to PipelineControls or read it from the selected config profile. Allow starting paper/live with any detector, not just CEXDEXArbDetector. | P1 |
| 6.4 | Wire the Config page adapter/sink/simulator settings through to PipelineManager so changing config actually affects pipeline behavior. | P1 |
| 6.5 | Add guidance text in the API Keys section: "Set these in your terminal with `export KEY=value` then restart `mev-kit ui`." Add a "Check Again" button that re-fetches /api/config/env. | P2 |
| 6.6 | Add a "Delete Profile" button with confirmation for non-default profiles. | P2 |

### Workflow 7: Monitor a Running Pipeline

**Current state:**
1. Dashboard has 8 components in a react-grid-layout drag/drop grid:
   - PipelineControls: mode dropdown + start/stop
   - MetricsStrip: P&L, WIN%, OPP/m, UPDATES, QUEUE, DETECT%
   - PnlChart: cumulative P&L line chart (lightweight-charts)
   - SpreadHistogram: spread distribution bar chart (recharts)
   - OpportunityFeed: scrollable trade list
   - LivePrices: DEX and CEX price + spread
   - HotParams: min_spread, position, fee_bps with edit/apply
   - LogStream: stub/placeholder

2. Data flows via WebSocket (`/api/pipeline/ws`) pushing metrics every 1 second
3. Layout is draggable and persisted to localStorage

**What works well:**
- The react-grid-layout is a nice touch for power users who want to customize their monitoring view
- MetricsStrip gives a dense, terminal-style overview of key numbers
- PnlChart uses lightweight-charts which is performant for real-time data
- WebSocket-driven updates avoid polling overhead

**Pain points:**
- **LogStream is a stub.** It says "Log streaming via WebSocket -- connect to /ws/logs" but there is no /ws/logs endpoint on the server. This panel takes up valuable screen real estate while providing no value.
- **LivePrices always shows dashes.** The Dashboard passes `dexPrice={null} cexPrice={null}` as hardcoded props. The WebSocket sends metrics but not individual price data. The LivePrices panel is cosmetically present but non-functional.
- **HotParams hardcodes initial values** (min_spread_bps: 15.0, position_size_sol: 0.01, fee_bps: 30.0) instead of reading from the active config or pipeline state. When the pipeline starts with different params, HotParams shows stale values.
- **HotParams APPLY silently fails** when no pipeline is running. The PATCH endpoint returns `{"status":"updated","params":["min_spread_bps"]}` even with no running pipeline -- it should return an error. (Bug in the pipeline_manager.py: `hot_reload` raises RuntimeError but the router catches it; however, tested via curl it returns "updated" not "error", suggesting the exception isn't reaching the router properly.)
- **OpportunityFeed has no pagination or scroll-to-top.** With 200 opportunities (the max buffer), the feed becomes a long scrolling list with no way to jump back to the latest.
- **No way to filter opportunities** by direction, success, or spread range in the feed.
- **PipelineControls stop button uses `alert()` for error handling** and `confirm()` for live mode warning. These browser dialogs break the design language.
- **No "connecting..." indicator** for the WebSocket. If the WS is disconnected/reconnecting, the UI shows stale data with no indication.
- **Grid layout saves to localStorage** but there's no "Reset Layout" button to get back to defaults.

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 7.1 | Implement LogStream: create a `/api/pipeline/ws` log channel (or a `/ws/logs` endpoint), stream structlog output, render in the panel with log-level color coding. Or remove the panel if log streaming is deferred. | P1 |
| 7.2 | Wire LivePrices to actual price data. The pipeline has access to both DEX and CEX prices -- push them via the WebSocket metrics payload or a separate field. | P1 |
| 7.3 | Initialize HotParams from the active config or pipeline state. On pipeline start, push current detector params via WebSocket; HotParams reads and displays them. | P1 |
| 7.4 | Replace `alert()` and `confirm()` in PipelineControls with styled confirmation modals matching the rest of the UI (the Modal component already exists). | P1 |
| 7.5 | Add a WebSocket connection status indicator on the Dashboard (green dot for connected, red for disconnected, yellow for reconnecting). The `connected` state already exists in `usePipeline` but is unused in the UI. | P1 |
| 7.6 | Add a "Reset Layout" button near the dashboard grid. | P2 |
| 7.7 | Add minimal filtering to OpportunityFeed (at least direction toggle: ALL/BUY/SELL). | P2 |
| 7.8 | Fix HotParams PATCH to properly return error when no pipeline is running. | P2 |

### Workflow 8: Learn About MEV

**Current state:**
1. Navigate to Learn page (BookOpen icon)
2. Left sidebar: "Documentation" header, "Guides" section with 6 guides, "Reference" section with "External Resources" link
3. Guides:
   - Getting Started with mev-kit
   - MEV on Solana: Concepts
   - How CEX-DEX Arbitrage Works
   - The mev-kit Pipeline
   - Writing a Custom Detector
   - Backtesting Your Strategy
4. Each guide rendered from Markdown with prose styling
5. Prev/Next navigation at bottom of each guide
6. External Resources: 5 categories (Solana Core, MEV & Block Building, DEX Protocols, Data & RPC, Python Libraries) with 16+ curated links

**What works well:**
- This is the strongest part of the UI. The guide content is comprehensive and well-written.
- Breadcrumb navigation (Docs > Guides > [Title]) provides orientation
- Prev/Next buttons enable sequential reading -- good for the beginner persona
- External Resources are well-curated and categorized
- Prose CSS styling is polished with proper code block formatting, tables, and blockquotes
- Guide icons in the sidebar give visual differentiation

**Pain points:**
- **Getting Started guide references `scripts/fetch_binance_history.py`** which may not exist or match the actual script filename (`scripts/fetch_historical.py` per CLAUDE.md). Users following the guide will get "file not found."
- **Getting Started guide says "Download CSV" and "Download Parquet" buttons exist** on the backtest results page. The actual results page only has a "Tweak & Re-run" button -- no export buttons.
- **No search functionality** across guides. With 6 guides this is manageable but will become a problem as content grows.
- **No "Try it" interactive elements.** Guides describe steps but don't link directly to the relevant UI page. E.g., "Click the Backtest tab" could be a clickable link to /backtest.
- **Code blocks in guides use `codehilite` syntax highlighting** but the language is not always specified, leading to inconsistent formatting.
- **No reading progress indicator.** For long guides (Getting Started is ~4000 words), users can't see how far through they are.

**Recommendations:**

### Workflow 9: Manage Data Files

**Current state:**
1. Navigate to Data page
2. File table with columns: Name, Size, Rows, Modified, Columns (truncated with +N), Actions (Preview, Download, Delete)
3. Preview opens a Modal with first 10 rows in a DataTable
4. Download triggers browser file download via /api/data/files/{name}/download
5. Delete shows a confirmation Modal, then removes the file
6. Refresh button reloads the file list

**What works well:**
- Preview modal is useful for quick data inspection without external tools
- Delete confirmation prevents accidental data loss
- Column display with truncation and full list on hover is space-efficient
- Download works correctly for file transfer

**Pain points:**
- **No file upload.** Users who generate Parquet files externally have no way to add them through the UI. Must manually copy to `./data/` directory.
- **No multi-select or batch delete.** Cleaning up multiple old files requires deleting one at a time.
- **No file renaming.** Files have auto-generated names like `binance_solusdt_1m_20260404_202927.parquet` which are informative but not user-friendly for distinguishing between runs.
- **Preview shows only 10 rows** with no way to page through more.
- **File size formatting is good** but there's no total storage usage indicator.
- **No sort on the file table.** Cannot sort by size, date, or row count.
- **Column metadata in the table is useful** but there's no schema details view (data types, null counts, min/max for numeric columns).

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 9.1 | Add a file upload drop zone (drag-and-drop + click to browse) that accepts .parquet files. | P1 |
| 9.2 | Add column sorting to the file table (click headers to sort by Name, Size, Rows, Modified). | P1 |
| 9.3 | Add a total storage usage indicator at the top of the file table (e.g., "5 files, 190 KB total"). | P2 |
| 9.4 | Add batch select checkboxes and a "Delete Selected" action. | P2 |
| 9.5 | Expand preview to allow paging (e.g., "Show more rows" button or pagination). | P2 |

### Workflow 10: Iterate on Strategy Params

**Current state (quant desk workflow):**
1. Open Backtest page, configure params (min_spread=20, fee=30, position=0.1)
2. Run backtest, view results
3. Click "Tweak & Re-run" button -- returns to config form
4. Adjust min_spread to 15, run again
5. View results -- but previous results are gone, no comparison possible
6. Must manually note results from each run (or screenshot)
7. Repeat for each param variation

**Pain points:**
- **No result history.** Each backtest run overwrites the previous results in the `_runner` singleton. There's no way to view or compare previous runs.
- **No param sweep or grid search.** Running 20 variations of min_spread_bps requires 20 manual runs with manual recording.
- **"Tweak & Re-run" does not pre-fill the form with the previous params.** It resets to defaults because `handleReset()` sets state to `{ state: "idle" }` and the config state remains at whatever the user last entered (this actually works because the config state persists in React state, but it's not explicitly designed -- it works by accident).
- **No export of backtest results.** The results page shows trades in a table but there's no CSV/Parquet export button (the Analysis page has export, but the Backtest page doesn't, and backtest results don't flow to the Analysis page).
- **No tagging or labeling of runs.** Cannot annotate a run as "conservative params" or "aggressive params."
- **No A/B comparison view.** Must open Analysis in a separate tab (if it worked) or rely on external spreadsheets.

**Recommendations:**

| # | Improvement | Priority |
|---|-----------|----------|
| 10.1 | Save backtest results to a run history (in-memory or SQLite). Show a "Recent Runs" panel on the Backtest page listing past results with their params and summary metrics. | P1 |
| 10.2 | Add a "Compare with Previous" button that shows the current and previous run's metrics side-by-side. | P1 |
| 10.3 | Add a CSV export button on the Backtest results page (the Analysis page has this but the Backtest page does not). | P1 |
| 10.4 | Add a "Param Sweep" mode that lets users specify a range for one parameter (e.g., min_spread_bps from 5 to 50 in steps of 5) and runs backtests for each value, presenting results in a table. | P2 |
| 10.5 | Add optional run labels or notes that can be attached to a backtest result. | P3 |
